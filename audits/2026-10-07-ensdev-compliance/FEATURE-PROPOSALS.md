# Prioritized feature proposals

Audit: **AUGENDA-ENSDEV-2026-10-07**. These are proposals, not approved requirements or implementation instructions. Existing obligations and optional additions are identified separately. Priority considers privacy/data loss, core-task dependence, compatibility and user burden; no invented delivery dates or budget thresholds are imposed.

## First: complete the protection features already required

| ID | Proposal | Why / existing basis | Concrete acceptance direction and dependencies |
| --- | --- | --- | --- |
| FP-01 | Recoverable Watch capture | Repair F-001; Constitution preservation and Handbook interruption/recovery controls. | A queued capture that cannot be applied stays available to its originating person. Show pending/rejected/recoverable status with retry, copy or authorized reassignment. Profile changes must not silently discard the thought or grant another profile access. Verify disconnect → capture → phone profile change → rejection → restart → recovery. |
| FP-02 | Explicit private and shared profile spaces | Repair F-002; purpose-scoped context, shared-record and supported-decision controls. | Inbox, focus picker/history, cognitive suggestions and AI memory obey the same declared authority model. Make deliberate sharing visible. Avoid introducing accounts merely to add authentication; first decide whether each profile represents a separate person or a customization of one person's experience. Test denied reads/writes/AI use/export and role changes using synthetic people. |
| FP-03 | One place to pause AI and see its request state | Repair F-003/F-004/F-005; AI controls, continuing authorization and resource/spending requirements. | Disabling AI prevents new queued work; cancellable work can stop; unavoidable committed effects are explained. Count provider usage independently of whether the user applies the proposal. Link minimal request/provider/model/authorization/change records to the affected task, with inspection and deletion. Distinguish **$0**, finite budget and Unlimited. Use fake providers before any live credentialed validation. |
| FP-04 | Supported first-launch route | Existing onboarding/CI requirement; see F-007 and verification limits. | One coordinator owns the initial capacity/profile/onboarding/morning sequence. Cold empty-store launch offers the capacity choice reliably, and low-capacity users can defer the tour without losing core access. Preserve current opt-in check-ins. Validate actual clean preferences as well as an empty model store. |

## Next: additions that fit AuGenda's purpose

| ID | Optional feature | User benefit | Proposed boundary and verification |
| --- | --- | --- | --- |
| FP-05 | Keep a capture as a note | A thought can remain information without becoming a demand. Aligns with Ontology's valid Observation → Note path and the independent-notes roadmap. | Inbox review offers Keep as note, Make task and Discard; independent notes can be searched locally. Retain source/time and explicit ownership. Requires a bounded PRD update and ownership/schema decisions; test no-AI/offline capture, search, correction, export and deletion. |
| FP-06 | Gentle routine-run history | Preserve what happened while allowing the reusable checklist to reset. Addresses C-001's mapping/retention question. | Show a repeatable plan separately from each retained run. Allow incomplete/abandoned runs and an optional short outcome rather than equating completion with success. Choose proportionate retention; do not retain indefinitely. Any new persistent model needs the next schema version, migration stage, prior-store fixture and failure tests. |
| FP-07 | A tiny starting step | Reduces initiation friction on low-capacity days, building on the existing Just Start surface. | Offer one user-chosen first step and a user-chosen bounded focus duration, with Stop/Not now always available. AI is optional and only proposes a preview. Test that declining or stopping does not mark the parent task completed or create pressure. |
| FP-08 | Voluntary body-double availability | Makes the existing body-double flag useful; AC-5.3.3 already calls for availability. | Each person chooses whether to advertise availability, to whom and for how long. No inferred presence or monitoring. Show Unknown separately from Unavailable. Task details may reveal a match only within permissions; verify expiry, withdrawal, offline staleness and absence of pressure notifications. |
| FP-09 | Inspectable suggestions with adjustable rules | Makes non-AI scaffolding understandable and correctable under Doctrine's assistance stance. | Explain which user inputs and enabled rule led to a suggestion; allow hiding/adjusting the relevant rule and retaining manual list access. Persist only minimal purpose-bound decision metadata where required. Separate “your reported capacity” from a fallible suggestion; test lock/pin, decline and rule-disable behavior. |
| FP-10 | Local handoff through Shortcuts and documented formats | Extends existing portability with native, user-directed capture and exchange. | Start with bounded capture/open/export actions; identify destination, selected records and effects. Receiving data grants no extra access or onward authority. Preserve duplicate handling, format versions, correction and revocation rules. Defer continuous cross-app delegation until its authority and partial-failure contracts are defined. |
| FP-11 | Capacity history with optional patterns | Can help someone remember what worked without turning completion into a performance demand. | Record deliberate, time-qualified self-reports per person; let the person inspect, correct, export and delete them. Patterns are labeled estimates and can be disabled. Avoid diagnosis requirements, clinical claims, automatic schedule changes and pressure scores. Requires privacy/retention and meaningful-outcome criteria before evaluation. |

## Sequence and constraints

Complete preservation and authority controls before adding broader household sharing, deeper AI memory or continuous automation. Repair documentation and adopt an identifiable PRD/governance baseline alongside those changes. Then select one small optional feature based on the user's actual friction rather than expanding all roadmap areas at once.

CloudKit, paid services, new accounts, custom cryptography, automated sharing, medical features, analytics SDKs and a rewrite are not prerequisites for these proposals. No recipient for citizen-science participation is proposed because no documented useful pathway was supplied.
